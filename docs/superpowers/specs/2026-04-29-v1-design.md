## 1. Product summary

A web application that an auction-selling business uses to receive, photograph, catalog, and manage used / pre-owned inventory; assign that inventory into auctions; and (in v2) prepare batch upload files for external auction platforms. The actual auctions run on third-party platforms — this system does not conduct live auctions.

The app is responsive and serves two surfaces from the same codebase:

- **Mobile** — primary tool for cataloging. Used by Warehouse staff with a phone-camera-driven workflow.
- **Desktop** — primary tool for administration. Used by Admin and Office staff for inventory browsing, auction management, lifecycle changes, AI runs, and user management.

There is no native mobile app.

---

## 2. Goals and non-goals

### v1 goals

- Mobile-first cataloging session: Warehouse staff photograph and register items as lots, one at a time
- Pre-session admin setup: select Customer + Job before a session begins
- Lot-based intake with photos, structured attributes, label printing, and conditional inputs
- AI-assisted title / description / reference-price generation, runnable manually or on an admin-configurable schedule
- Desktop inventory management: filterable browse, faceted search, bulk actions, lifecycle state changes
- Auction assignment (where Auction = Job)
- Audit log over critical entities, admin-only reporting

### Non-goals (deferred to v2)

- Multi-platform export — admin-configurable platform mapping templates and batch upload file generation for external auction platforms
- Scheduled batch removal of audit_log entries (v2)
- Configurable monthly AI-spend budget (v2)

### Out of scope for v1 (some may be revisited in future versions)

- Buyer-facing or public-facing UI
- Multi-tenancy (no plans to add)
- **Native mobile app** — out of scope for v1; may be added in a future version if mobile-browser limits warrant it
- **Direct API integration with auction platforms** — out of scope for v1; may be added in a future version. v2 already covers file-based batch upload, which may suffice indefinitely.
- Live in-app auction conduct (no plans to add)

## 3. Roles, access, and permissions

Three roles. Single-tenant; RBAC is role-only (no tenant dimension).

- **Admin** — full system access; manages users, customers, jobs, system config
- **Office** — desk-based work: manages auctions / jobs, edits inventory, drives lifecycle, runs AI
- **Warehouse** — primary mobile cataloger; can also view and edit any lot from any surface; **no bulk actions**

### Permission matrix

| Capability | Admin | Office | Warehouse |
|---|---|---|---|
| **Customer & Job** |
| View customers / jobs | ✓ | ✓ | ✓ (limited — pick from list to start session) |
| Create / edit customer | ✓ | ✓ | ✗ |
| Create / edit job | ✓ | ✓ | ✗ |
| Delete customer / job | ✓ | ✗ | ✗ |
| **Cataloging session** |
| Start a session | ✓ | ✓ | ✓ |
| Capture lot (photos + fields) | ✓ | ✓ | ✓ |
| Save lot (Next) | ✓ | ✓ | ✓ |
| **Lot — view & edit** |
| View all lots | ✓ | ✓ | ✓ |
| Edit lot fields post-save | ✓ | ✓ | ✓ |
| Edit / add lot photos post-save | ✓ | ✓ | ✓ |
| Delete lot | ✓ | ✗ | ✗ |
| **Lot state changes** |
| Mark sold / picked up / not-sellable | ✓ | ✓ | ✗ |
| **Auction (Job) management** |
| View auctions | ✓ | ✓ | ✗ |
| Create / edit / delete auction | ✓ | ✓ | ✗ |
| Assign lots to auction | ✓ | ✓ | ✗ |
| **AI** |
| Trigger AI run manually | ✓ | ✓ | ✗ |
| Configure AI schedule | ✓ | ✗ | ✗ |
| **System / users** |
| Manage users + role assignments | ✓ | ✗ | ✗ |
| System config | ✓ | ✗ | ✗ |

Editing of lot fields is also gated by **lifecycle state** — see §6.

### Auth and authorization

- **Auth provider:** Supabase Auth.
- **JWT custom claims:** the role is synced into `app_metadata.role` at token issuance via a Postgres-function-backed Custom Access Token Hook.
- **JWT signing:** modern Supabase signs access tokens with **ES256** (asymmetric ECDSA). The public key is published at `<SUPABASE_URL>/auth/v1/.well-known/jwks.json`. The Hono auth middleware verifies tokens against this JWKS using `jose.createRemoteJWKSet` — **no shared `JWT_SECRET` is stored anywhere**. Tests mint their own ES256 tokens and inject a local JWKS into the middleware via a test-only escape hatch.
- **RLS:** every public-schema table has RLS enabled. Policies read role via `auth.jwt() -> 'app_metadata' -> 'role'` — no JOIN to `app_user` per query.

### RLS strategy summary

- `customer`, `job`: SELECT open to all authenticated; mutations gated to `('admin', 'office')`; DELETE admin-only.
- `lot`, `lot_photo`: SELECT and INSERT open to all authenticated roles; UPDATE open when lot.state ∈ {`assigned`, `unassigned`}, blocked otherwise except for legal state transitions; DELETE admin-only.
- `app_user`: SELECT and UPDATE admin-only.
- `system_settings`: SELECT all authenticated; UPDATE admin-only.
- `audit_log`: SELECT admin-only; INSERT trigger-driven.

### Surface mapping

| Role | Mobile | Desktop |
|---|---|---|
| Warehouse | **Primary** (cataloging) | Allowed via responsive layout |
| Office | Allowed | **Primary** |
| Admin | Allowed | **Primary** |

## 4. Data model

All tables in the public schema. UUIDs for PKs unless otherwise noted.

### `app_user`

Mirror of `auth.users` carrying app-level user data.

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | uuid | yes | PK; FK to `auth.users.id` |
| `role` | enum (`admin` / `office` / `warehouse`) | yes | Synced to JWT `app_metadata.role` via Custom Access Token Hook |
| `display_name` | text | yes | Free-form |
| `disabled_at` | timestamptz | no | Soft-deactivation marker |
| `created_at`, `updated_at` | timestamptz | yes | Audit |

### `customer`

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | uuid | yes | PK |
| `name` | text | yes | Free-form. Only required field. CRM data lives elsewhere. |
| `created_at`, `updated_at` | timestamptz | yes | Audit |

### `job`

A `(customer, job)` pair represents an auction. There is no separate `auction` entity. Job CRUD lives on the Customer detail page in the admin shell (D-006).

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | uuid | yes | PK |
| `customer_id` | uuid (FK → customer) | yes | A job is owned by exactly one customer |
| `job_number` | text | yes | Admin-entered free-form. Unique within `(customer_id, job_number)` |
| `closed_at` | timestamptz | no | NULL = open; non-NULL = closed. Closed jobs appear **grayed (visible-but-disabled)** in the cataloging picker (D-005). Closed jobs can still be selected as filter values on Inventory. |
| `created_at`, `updated_at` | timestamptz | yes | Audit |

Constraint: `UNIQUE(customer_id, job_number)`.

### `lot`

The unit of cataloging. One lot record may represent one physical item or several (~10% of the time AI detects multi-item lots and adjusts the description accordingly).

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | uuid | yes | PK; stable internal identifier (not displayed) |
| `job_id` | uuid (FK → job) | conditional | NOT NULL when `state ∈ {assigned, sold, picked-up}`; NULL when `state ∈ {unassigned, not-sellable}` |
| `lot_number` | integer | conditional | Same nullability as `job_id`. Starts at 10 per job, +1 per new lot. Partial unique index: `UNIQUE(job_id, lot_number) WHERE job_id IS NOT NULL` |
| `quantity` | integer | no | Backfillable |
| `title` | text (≤ 50 chars) | no | AI-generated per the title format spec (§9.4) |
| `description` | long text | no | AI-generated body + conditional suffixes (§9.5) |
| `price` | numeric(10, 2) | no | Reference price (best available new-condition retail). When NULL, title rendering substitutes `$$$`. |
| `condition` | enum | yes (default value) | **Hidden in v1 UI.** Carried in schema with a default; vocab + UI exposed in a later iteration. |
| `ref1` | text (single line) | no | General-purpose |
| `ref2` | text (single line) | no | General-purpose |
| `special_notes_category` | enum (`None` / `TOOL ONLY` / `READ` / `CLOTHING`) | yes (defaults `None`) | Drives title / description suffixes. Each option carries a `requires_text` flag in front-end config; `CLOTHING` is the only v1 option that does. |
| `special_notes_text` | text | conditional | Required when the selected option's `requires_text` is true. For `CLOTHING`, label and stored value is `size`. |
| `untested` | boolean (default `false`) | yes (auto, defaults false) | Operator-set checkbox at intake. When `true`, description rendering appends ` UNTESTED`. |
| `last_ai_run_status` | enum (`success` / `partial` / `failure`), nullable | no | Set after each AI run; drives status icons in inventory list |
| `last_ai_run_error` | text, nullable | no | Short error message for `partial` / `failure` cases; shown in lot detail modal |
| `state` | enum (`assigned` / `unassigned` / `sold` / `picked-up` / `not-sellable`) | yes | Initial state on cataloging is `assigned`. State machine in §6.1 |
| `intake_operator_id` | uuid (FK → app_user) | yes | Set from auth context at creation |
| `intake_timestamp` | timestamptz | yes | Set on creation |
| `created_at`, `updated_at` | timestamptz | yes | Audit |

### `lot_photo`

| Field | Type | Required | Notes |
|---|---|---|---|
| `id` | uuid | yes | PK |
| `lot_id` | uuid (FK → lot) | yes | One lot has one or more photos |
| `storage_path` | text | yes | Supabase Storage object path; deterministic, set at capture time |
| `display_order` | integer | yes | For ordering / picking primary photo |
| `status` | enum (`pending` / `uploaded` / `failed`) | yes | Created at capture as `pending`; flipped to `uploaded` when the file lands |
| `captured_at` | timestamptz | yes | Audit |
| `captured_by` | uuid (FK → app_user) | yes | Audit |

`lot_photo` is **excluded from audit_log scope** — `captured_by` is sufficient.

### `system_settings`

| Field | Type | Notes |
|---|---|---|
| `id` | int | Always `1`; check constraint enforces single-row |
| `ai_schedule_enabled` | boolean (default `true`) | |
| `ai_schedule_frequency` | enum (`hourly` / `daily`) (default `daily`) | |
| `ai_schedule_time_of_day` | time (default `23:00`) | Used when frequency = `daily` |
| `ai_last_run_at` | timestamptz, nullable | Updated by the AI batch endpoint |

| Field | Type | Notes |
|---|---|---|

| `table_name` | text | |

## 5. Mobile cataloging workflow

The most-used surface in the app. Optimized for one-handed warehouse use, big tap targets, minimal typing.

### 5.1 Pre-session

Operator logs in, lands on a Customer / Job picker:

1. Pick a customer (searchable dropdown).
2. Pick a job for that customer (searchable dropdown, scoped). **Closed jobs (`closed_at IS NOT NULL`) are visible but disabled** in the picker (D-005) — the operator can see them but can't catalog into them.
3. Tap **Begin Session**.

### 5.2 Per-lot intake loop

After session begins, system displays a fresh **Lot in progress** screen with the next available `lot_number` reserved (starts at 10 per job, +1 per new lot). The lot is in transient client-side state `in_progress` until first save — no DB row exists yet.

1. Operator taps **camera** — device's native camera opens (via `<input type="file" accept="image/*" capture="environment">`). Take one photo, control returns to the lot screen with the new photo as a thumbnail in the strip below the lot fields. Repeat for additional photos (min 1, max 12, both config-driven). The first photo is treated as the **cover** (badge in UI; `display_order = 1` in storage).
2. Operator can tap any thumbnail to retake / delete / reorder. Long-press to drag-reorder on mobile.
3. Operator selects **Special Notes** (defaults to `None`). When `CLOTHING` is selected, a `Size` text field surfaces.
4. Operator may check the **Untested** checkbox.
5. Operator may optionally fill any of `Title`, `Description`, `Quantity` (default 1), `Price`, `Ref1`, `Ref2` — all backfillable later. Background autosave runs ~1.5 s after edits stop.
6. Operator taps **Print Label** to print on demand (D-004). Print is **manual**, not auto-on-Next, so a misbehaving printer never blocks the cataloging flow.
7. Operator taps **Next** to save the lot. The system: increments `lot_number` by 1, presents a fresh Lot in progress screen. **No automatic label print** on Next.
8. Or taps **New Catalog** to exit the session and return to the Customer / Job picker.

Print failures appear as a top-of-screen amber toast that does not block save.

### 5.3 Phone configuration assumptions

- Phones set to **lowest resolution (12 MP)**.
- iPhones configured to **Settings → Camera → Formats → Most Compatible** so output is JPEG, not HEIC. One-time device setup; eliminates client-side HEIC conversion.

## 6. Photo capture pipeline

### 6.1 Bounds

- Minimum: 1 photo per lot (gate to advance).
- Maximum: 12 photos per lot.
- Both config-driven.

### 6.2 Upload model

Async, non-blocking.

- Direct **browser → Supabase Storage** via signed URLs. The Hono API never proxies image bytes.
- A `lot_photo` row is created **at capture time** with `status='pending'` and a deterministic `storage_path`. Status flips to `'uploaded'` when the file lands.
- Upload queue is **IndexedDB-backed** so pending uploads survive a tab close, browser refresh, or device sleep.
- Operator can save the lot (Next) while uploads are still pending; they continue in the background and link to the saved lot via `lot_photo.lot_id`.
- A small persistent indicator shows pending count. If it exceeds a threshold (~10–20, tunable), captures pause until the queue drains.

### 6.3 Storage and serving

Originals are stored at 12 MP JPEG. Right-sized variants are served on demand via **Supabase Image Transformations** (`?width=1568&quality=80` style). Supabase caches transformed outputs.

| Use case | Size served | ~Per-image egress |
|---|---|---|
| Inventory browse thumbnails (desktop) | ~300 px | ~30 KB |
| Lot detail / mobile preview | ~1200–1600 px | ~250 KB |
| AI vision evaluation | 1568 px | ~400 KB |
| Auction platform export (v2) | original 12 MP | ~3–4 MB |
| "View full size" on demand | original 12 MP | ~3–4 MB |

Claude vision auto-resizes to ~1568 px regardless, so larger inputs offer no quality gain.

## 7. Lifecycle and state machine

### 7.1 States

| State | Meaning | `(customer, job, lot)` | Editable fields? |
|---|---|---|---|
| `assigned` | In an auction; default for newly cataloged lots | NOT NULL | yes |
| `unassigned` | Not currently in an auction; available for re-assignment | NULL | yes |
| `sold` | Sold at the auction it was in; awaiting pickup | NOT NULL | **frozen (amended D-001 — see §15)** — preserves the record shown to bidders |
| `picked-up` | Sold and collected; **terminal** | NOT NULL | **frozen — no edits** |
| `not-sellable` | Determined unsellable; **terminal** | NULL | **frozen — no edits** |

`in_progress` is a **client-side-only transient state** during the mobile cataloging flow before a lot is first saved. It is not persisted as a stored DB state.

### 7.2 Transitions

| From → To | Trigger | Roles | Side effect on `(customer, job, lot_number)` |
|---|---|---|---|
| (creation: first photo) → `assigned` | Auto on lot creation | Warehouse, Office, Admin | Set from active session |
| `assigned` → `sold` | Manual: marked sold after auction | Office, Admin | No change |
| `assigned` → `unassigned` | Manual: removed from auction | Office, Admin | **Cleared** |
| `assigned` → `not-sellable` | Manual: marked not-sellable | Office, Admin | **Cleared** |
| `unassigned` → `assigned` | Manual: assigned to a different auction | Office, Admin | New tuple set; `lot_number` = next available in destination job |
| `unassigned` → `not-sellable` | Manual: marked not-sellable | Office, Admin | (already cleared) |
| `sold` → `picked-up` | Manual: buyer collects | Office, Admin | No change |
| **`sold` → `unassigned`** | Manual: sale falls through (buyer never pays / picks up); lot returns to inventory for reassignment | Office, Admin | **Cleared** |
| `picked-up` | **Terminal** — no exit | — | — |
| `not-sellable` | **Terminal** — no exit | — | — |

### 7.3 Confirmation prompts

Transitioning into a terminal state (`picked-up` or `not-sellable`) prompts the user with a confirmation modal before commit. Hard-delete operations also prompt.

### 7.4 "Move to another auction" composite action

UI surfaces this as one action that internally executes `assigned → unassigned → assigned (with new tuple)`. The lot's state remains `assigned` from the user's perspective.

### 7.5 Editing rules

- **Editable in any field:** `assigned`, `unassigned`.
- **Frozen (read-only in UI):** `sold`, `picked-up`, `not-sellable`. Field-edit affordances disappear from the lot detail modal; server returns 422 `FROZEN` on any field PATCH.
- Frozen states still permit: legal state transitions, label reprint, and Delete (admin only).
- Edits on a sold lot are made by transitioning sold → unassigned, editing in unassigned, then assigning to a job (which transitions to `assigned`).

### 7.6 Default browse filtering

Default Inventory view hides `picked-up` and `not-sellable`. Both remain queryable via the State filter.

### 7.7 Stable identifier

When a lot is `unassigned` or `not-sellable`, its `(customer, job, lot_number)` is null. The system identifies such lots internally by `lot.id` (the existing UUID PK) — never displayed to users, never on a label, but always queryable. No new column needed.

For inventory list rows of unassigned lots, the primary identifier slot displays the lot's `title` (or `—` if title is null). Thumbnail and state badge are always present.

### 7.8 Delete

- Hard delete only, no soft-delete.
- Admin-only.
- Confirmation modal before commit.
- Audit log captures the deletion event.
- Rare in practice — lifecycle states cover day-to-day "remove from inventory" needs.

## 8. Inventory management workflow

### 8.1 Architecture

A single **Inventory** page covers all browse use cases — and is the **single action hub** (D-002): all filtering, search, and selection lives here. Per-lot actions are reached by clicking a row (lot detail modal). Bulk actions are reached by selecting rows and using the bulk-action bar; bulk dialogs do **not** re-list the selected lots.

There is **no separate Auctions page** (D-006). "View this auction" = filter the Inventory page by Customer + Job. Job CRUD lives on the Customer detail page in the admin shell.

### 8.2 Desktop layout

- **Top bar:** free-text search · saved-filter-preset dropdown · "Save current as preset"
- **Left sidebar — faceted filters:**
  - Customer
  - Job (cascades when customer is selected)
  - Lot state (multi-select: `assigned` · `unassigned` · `sold` · `picked-up` · `not-sellable`)
  - Date cataloged (range)
  - Special Notes category
  - Boolean filters: `Has title` · `Has description` · `Has price`
  - AI run status (multi-select: `success` · `partial` · `failure` · `not yet run`)
- **Main pane:** results list, **compact rows by default**, with a toggle to **cards-with-thumbnails**. Compact-row content: thumbnail + `Customer · Job · Lot` + title + state badge + AI status icon (when partial/failure)
- **Toolbar:** sort dropdown · results count · multi-select toggle / row checkboxes
- **Bulk-action bar (when selection non-empty):**
  - **Move** (to another auction) — destination job picker
  - **Change state** — only target states that are legal for **every** lot in the current selection are offered (D-003). If selection has mixed states with no shared legal target, the action is disabled with explanation.
  - **Run AI on selected**
  - **Export selected to CSV** (basic; template-driven export is v2)
  - **Delete** (admin only) — destructive styling, requires typing-confirm
- Bulk dialogs do **not** re-list the selected lots (D-002) — the user already chose them; dialogs focus on the action only.

### 8.3 Sort

Default: date cataloged, newest first. Options: Date cataloged · Customer (A→Z / Z→A) · Lot number · State.

### 8.4 Pagination

Virtualized infinite scroll. Selection persists across loaded results.

### 8.5 Selection / detail interaction

- Each row has a checkbox; toggling adds the row to the selection.
- Clicking the row body opens the **lot detail modal**.

### 8.6 Lot detail modal

- Photo gallery: large image + thumbnail strip + arrow controls on the image to step through photos. First photo (display_order = 1) is the **cover** with a UI badge.
- Forward/back lot navigation arrows when entered from a multi-select context.
- **Editable fields** when the lot is in `assigned` or `unassigned`. **Read-only** when state ∈ {`sold`, `picked-up`, `not-sellable`}; the modal header displays a "🔒 Read-only" pill.
- **Reprint Label** button — available in all states.
- **State** menu — legal transitions only; transitioning into terminal states (`picked-up`, `not-sellable`) surfaces a confirmation modal. The `sold → unassigned` transition (sale fall-through) is offered from sold lots.
- **Move to another auction** — for `assigned` lots; opens a destination-job picker.
- **Delete** — admin-only; confirmation modal.
- **No history tab** — audit history is admin-only via a separate reporting view.

### 8.7 Mobile inventory page (Warehouse-focused)

- Sticky top bar: search input · filter button (opens slide-out drawer)
- Slide-out filter drawer: same filter set as desktop
- Results: single-column compact rows
- Tap a row: opens the lot detail modal full-screen
- **No multi-select / bulk actions on mobile**

## 9. AI subsystem

### 9.1 What AI does

Generates **title**, **description**, and **reference price** for each lot, and detects multi-item lots. Runs on lots with null fields. Output is editable post-generation.

### 9.2 Lookup path (preferred when item is identifiable)

When AI can identify the lot's product, it uses tool calls to look up product information.

- **v1 lookup tool:** Anthropic web search. Built into Claude's tool-use; no separate vendor contract.
- **Architecturally pluggable:** future structured product-data API (RapidAPI / SerpAPI / eBay Browse / etc.) can be added as a `product_lookup` tool that Claude chooses between as appropriate. No refactor required.

### 9.3 Generation path (fallback)

When the item can't be identified, AI generates from photos + operator-provided fields (`quantity`, `special_notes_category`, `special_notes_text`, `untested`, `ref1`, `ref2`).

### 9.4 Title format spec

Hard maximum 50 characters.

```
$<price>- <quantity>x <brand> <brief description>[ <special note>]
```

- `<price>`: numeric reference price. When `lot.price IS NULL`, substitute `$$$` for `$<price>` in the rendering layer.
- `<brand>` and `<brief description>`: AI-extracted, not stored as columns.
- `<special note>` appended only for `TOOL ONLY` and `READ` (not for `CLOTHING` or `None`).
- Brief description is **truncated** to fit the 50-char limit when the special-note suffix is appended.

### 9.5 Description format spec

AI generates the description body. Conditional suffixes:

- If `special_notes_category = CLOTHING` → append ` CLOTHING - <special_notes_text>` (the size).
- If `untested = true` → append ` UNTESTED` (capitalized).

Both suffixes can apply to the same lot.

### 9.6 `special_notes_category` v1 list

| Option | Surfaces text input? (label) | Appends where? |
|---|---|---|
| `None` (default) | no | nowhere |
| `TOOL ONLY` | no | end of title |
| `READ` | no | end of title |
| `CLOTHING` | yes (`Size`, stored in `special_notes_text`) | end of description as `CLOTHING - <size>` |

The list is config-driven. Adding a new option that fits the existing append patterns requires no code; an option needing custom append logic does.

### 9.7 Multi-item lot detection

AI inspects the photos. When multiple distinct items are visible (~10% case), the brief description / description reflect that. AI does not override the operator's `quantity`. No new schema or UI surface.

### 9.8 Triggers

**Manual:**
- `Run AI` button on the lot detail modal (single)
- `Run AI on selected` in the inventory bulk-action bar

**Scheduled:**
- Driven by `system_settings`:
  - `ai_schedule_enabled` (on/off)
  - `ai_schedule_frequency` (`hourly` / `daily`)
  - `ai_schedule_time_of_day` (when daily)
- Implementation pattern: **Vercel Cron runs every hour**, hits a Hono endpoint that reads `system_settings`, decides whether to actually run, and processes lots needing AI. Avoids a redeploy when scheduling changes.
- Default config: enabled, daily, 23:00.

### 9.9 Per-run logic

For each lot processed:

1. Fetch photos at 1568 px from Supabase Storage via Image Transformations.
2. Build prompt with photos + operator-entered fields + format rules.
3. Call Claude (with `web_search` tool available).
4. Parse structured response: `title`, `description`, `price`, `brand`, `brief_description`, `multi_item_detected`.
5. Render final title using the format spec; render final description with appended suffixes.
6. Update lot fields. Audit log captures the change.
7. Set `last_ai_run_status` (`success` / `partial` / `failure`); populate `last_ai_run_error` on partial / failure.

**Status semantics:**
- `success` — all three target fields (`title`, `description`, `price`) were generated.
- `partial` — at least one target field was generated and at least one was missing/failed. UI derives per-field state from which fields are null. The `last_ai_run_error` records why the missing field(s) failed.
- `failure` — none of the target fields were generated.
- `null` — the lot has not yet been processed by AI.

### 9.10 Failure / partial-result UX

- Inventory list rows show a small icon when `last_ai_run_status` is `failure` or `partial`.
- Inventory filter includes "AI run status".
- Lot detail modal displays `last_ai_run_error` near the AI-generated fields when status is `failure` or `partial`.
- No automatic retry queue. Office can manually re-run via the bulk-action bar.

### 9.11 Cost guardrails

For v1: **no hard cap on AI spend.** Per-call cost kept low by 1568 px image inputs (Round 2 outcome). Per-lot cost ~$0.01–$0.05; 1,000 lots ≈ $50–$100/month. Monitoring via Anthropic's billing dashboard. v2 can add a configurable monthly budget — additive change, no schema or architecture impact.

## 10. Label printing

### 10.1 Hardware and integration

- **Printer:** Zebra ZD450 (already owned).
- **Integration:** **Zebra Browser Print** — free helper service from Zebra running on the workstation. The web app sends ZPL over `localhost`; the helper relays to the printer over USB. No vendor lock-in beyond the helper itself.

### 10.2 Label format

- **Size:** 2" wide × 1" tall (landscape). At 203 dpi → 406 × 203 px usable area.
- **Print trigger:** **manual** (D-004). The mobile cataloging UI has an explicit **Print Label** button. Tapping **Next** saves the lot but does **not** invoke the printer. This keeps printer issues from blocking save and removes "did the printer eat my label?" cognitive load from every lot. The same **Reprint Label** button is available on the lot detail modal in all states for desktop reprinting.

### 10.3 Label content

```
+----------------------+
|        | Lot 13      |
|  [QR]  | Smith       |
| ~120px | 2026-04-001 |
+----------------------+
```

Fields (in priority order — drop bottom items if they don't fit):

1. **QR code** (left, ~120 × 120 px at 203 dpi — fills ~60% of label height)
2. **Lot number** (large, top of right column)
3. **Customer name** (truncated if needed)
4. **Job number** (truncated to last segment if needed, e.g. `001` instead of `2026-04-Smith-001`)

Intentionally not on the label: title, description, price, category, special notes, date cataloged, operator (was on the original 4"×2" layout but dropped on 2"×1" for legibility — recoverable via QR scan since auth-gated lot detail page surfaces all metadata).

> **Implementation note:** the exact ZPL template, font sizing, and final field set remain open per §14 (Round 4) — to be tuned against the physical printer with actual sample lots. The list above is the priority guide.

### 10.4 QR encoding

URL of the form `https://<auction-os-domain>/lot/<lot.id>`. Any phone QR scanner opens the lot directly. Auth gates the lot view. Production domain set at deployment.

### 10.5 Reassignment behavior

When a lot is moved to another auction, the original printed label's `(customer, job, lot)` becomes stale. **No automatic reprint.** The QR continues to scan to the right record. Reassignment is brief in practice and relabeling isn't required.

### 10.6 Reprint

Available via a button on the lot detail modal. All states.

## 11. Audit log

### 11.1 Approach

Single `audit_log` table populated by **Postgres triggers** on tracked tables. No app-level audit calls.

### 11.2 Tracked tables

`lot`, `customer`, `job`, `app_user`. (`lot_photo` excluded — `captured_by` is sufficient.)

### 11.3 Captured

Full before / after diff per change (insert / update / delete).

### 11.4 Visibility

**Admin-only** via a dedicated reporting view inside the admin section. Non-admin roles never see audit data. The lot detail modal does not show audit history.

### 11.5 Retention

- v1: indefinite.
- v2: scheduled batch-removal of old entries to manage Supabase storage. Retention policy defined when v2 begins.

## 15. Design handoff and accepted deviations

A separate UI design pass produced visual mockups in `ui-design/design_handoff/` (Option C · Mica Slate, three implementation HTML files plus JSX sources). The design handoff folder is the source of truth for visuals; this spec captures the resulting behavioral and schema decisions.

### Accepted deviations from the original spec

The design pass surfaced six tracked deviations and several additional items reviewed during reconciliation. All have been accepted and are reflected throughout this spec.

| ID | Topic | Resolution |
|---|---|---|
| D-001 | `sold` is editable | **Amended 2026-05-01: sold is now frozen.** Originally accepted as editable to allow corrections after a sale. Reversed during Phase 2 sign-off testing: sold lots preserve what bidders saw on the auction platform, and edits would mutate the record of what was sold. To edit a sold lot, transition sold → unassigned, edit, then re-assign. Frozen states are now `sold`, `picked-up`, `not-sellable`. |
| D-002 | Inventory is the single action hub | Accepted. All filtering and selection live on Inventory; bulk dialogs don't re-list selected lots. |
| D-003 | Bulk Change-state shows shared transitions only | Accepted. Mixed selections with no shared legal target → action disabled with explanation. |
| D-004 | Manual Print Label button | Accepted. Cataloging Next saves but does not print; explicit Print Label button on the cataloging UI; lot detail modal has Reprint in all states. |
| D-005 | Closed jobs grayed (visible-but-disabled) in picker | Accepted. Implemented via new `job.closed_at` field. |
| D-006 | No separate Auctions page | Accepted. Job CRUD lives on Customer detail page; "view auction" = Inventory filtered by (Customer, Job). |

Additional items reviewed and accepted:

- **`sold → unassigned` transition added** — for sale fall-through (buyer never pays / picks up). Clears `(customer, job, lot_number)`.
- **`in_progress` is a UI-only transient state** during mobile cataloging before first save — not persisted as a DB state.
- **AI status interpretation** — `partial` means at least one target field generated and at least one missing/failed; UI derives per-field status from which fields are null.
- **Cover photo concept** — first photo (`display_order = 1`) is the cover; UI shows a badge.
- **Background autosave** during mobile cataloging (~1.5 s after edits stop).
- **Sale tracking fields** (sold price, buyer ref, picked-up date, not-sellable reason) are **out of scope for v1** per user decision; revisit if needed.
- **Native mobile app** and **direct API integration with auction platforms** are out of scope for v1 but **may be added in a future version**.
