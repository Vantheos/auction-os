# Phase 5 Implementation Plan — Auction Platform Export

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended for token-budget reasons) or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the AF360 / HiBid CSV + batched image zip export pipeline. Add `customer.seller_code` (nullable, app-required), `customer.disabled_at` (soft-deactivation), `job.start_bid` + `job.shippable` (Job-level export defaults). Build new edit forms for both Customer and Job (neither entity has an editable surface today). Customer → Job → "Export to AF360" action produces 1 CSV (inline) + N image zips (server-built, uploaded to Vercel Blob, downloaded sequentially). Read-only Settings → Auction Platforms panel.

**Architecture:** Continues Phase 1–4 patterns. Native Vercel `(req, res)` handlers, Drizzle migrations, React + Vite + TanStack Query + shadcn primitives. New server dep: `archiver` (Node streaming zip, ~1MB unpacked). New service dep: Vercel Blob (temp store for image zips, 24h TTL via cleanup cron). All mutations through `asActor(userId, fn)`. All new mutation hooks gated by `docs/testing-policy.md` (invalidation + error toast tests).

**Spec reference:** [`docs/superpowers/specs/2026-05-04-phase-5-design.md`](../specs/2026-05-04-phase-5-design.md) is authoritative for design decisions.

**Source spec:** [`docs/auction-platform/AF360_HiBid_Lot_Import_Spec.md`](../../auction-platform/AF360_HiBid_Lot_Import_Spec.md) — authoritative for AF360 CSV format + image filename convention.

**Branch:** `phase-5-auction-platform-export` off `phase-4-settings-users` (`fc2bb25`).

### D2. `/start` business logic

- [ ] Resolve job + its customer; 404 NOT_FOUND on miss
- [ ] Reject `400 SELLER_CODE_REQUIRED` if `customer.sellerCode` is null or empty
- [ ] Query lots: `state = 'assigned' AND job_id = :id`, ordered by `lotNumber ASC`
- [ ] Reject `400 NO_LOTS` if zero lots
- [ ] Build `ExportContext[]` for each lot, then `buildAF360Csv(...)` from Phase A
- [ ] Compute batch plan: chunks of `BATCH_SIZE = 100` lots; emit `batches: [{ batchNum, lotIds }]`
- [ ] Compute `exportLabel = "JobExport-{slugify(customer.name)}-{job.jobNumber}-{YYYY-MM-DD}"`
- [ ] Compute `csvFilename = "{exportLabel}.csv"`
- [ ] Return JSON per spec §3.5
- [ ] Test in `tests/api/jobs-export-af360-start.test.ts`: each rejection path; happy path with 250-lot fixture → 3 batches; CSV content correct

### D3. `/batch` endpoint scaffold

- [ ] Create `api/jobs/[id]/export-af360/batch.ts`:

  - Method gate: only POST
- [ ] Test: 401, 403 warehouse, 405 wrong method, 400 INVALID_BODY for malformed body

### D4. `/batch` lot validation (defense against tampering)

- [ ] Verify all `lotIds` exist, belong to this job, and are in `assigned` state
- [ ] Reject `400 INVALID_LOT_IDS` if any fail validation
- [ ] Test: tampered lotIds (different job, wrong state, non-existent) all rejected

### D5. `/batch` photo fetch + filename normalization

- [ ] Query `lot_photo` rows for these lots, ordered by `displayOrder` per lot, `status = 'uploaded'` only
- [ ] Compute filename per AF360 convention:
  - 1 photo: `{lotNumber}.jpg`
  - 2+ photos: `{lotNumber}-{order}.jpg` where `order` is 1-indexed display position
- [ ] Reject `500 EXPORT_FAILED` if any photo `storagePath` doesn't end with `.jpg` or `.jpeg`; include affected lot numbers in error message
- [ ] Test: lot with 1 photo, lot with 3 photos, lot with mixed format → EXPORT_FAILED

### D6. `/batch` zip stream + Vercel Blob upload

- [ ] Use Supabase admin client `download(path, { transform: { width: 1568, quality: 80, resize: 'contain' } })` to fetch each photo as a Blob/Buffer (server-side; not via signed URL)
- [ ] Use `archiver('zip', { store: true })` to build the zip stream (no compression — JPEGs already compressed)
- [ ] As each photo arrives: `archive.append(buffer, { name: filename })`
- [ ] Parallelism: ~50 concurrent photo downloads (use a small queue helper or `p-limit` if needed; or simply chunk + `Promise.all` in groups of 50)
- [ ] When all photos appended: `archive.finalize()`
- [ ] Stream the archiver output directly into Vercel Blob `put(path, stream, { access: 'public', addRandomSuffix: false, token: process.env.BLOB_READ_WRITE_TOKEN })`
  - Path: `exports/{jobId}/{exportLabel}-batch-{batchNum}-of-{totalBatches}.zip`
- [ ] Note: `totalBatches` derived from re-computing the batch count for the job (or accepting it from request body for simplicity)
- [ ] Test: mock Supabase download + Vercel Blob put → verify zip filename pattern, photo count, archiver-append calls

  - `start(jobId)` flow:
    1. POST `/start` → receive `{ csv, csvFilename, batches, totalBatches, exportLabel }`
    2. Convert CSV string to Blob (`new Blob([csv], { type: 'text/csv' })`)
    3. Trigger CSV download via synthetic anchor (`<a href={objectUrl} download={csvFilename}>` programmatic click + revoke URL)
    4. For each batch in `batches` (sequential):
       - Update status to `batch-{N}-of-{M}`
       - POST `/batch` with `{ batchNum, lotIds, exportLabel }`
       - On response: update status to `downloading-{N}-of-{M}`, trigger anchor download of `downloadUrl`
       - On error: set status to `error`, halt; expose `retryFromBatch(N)` for resume

## Risk register

| Risk | Mitigation |
|---|---|
| `archiver` Vercel function compatibility | Standard Node module; widely used in serverless contexts. Verify with a minimal smoke test in D6 before building full pipeline. |
| Vercel Blob latency from Vercel function (upload phase) | Same network; typically fast. If upload > 60s for a 200MB batch zip, investigate. Fallback: smaller batch size. |
| Per-batch function timeout (300s) | Conservative batch size of 100 lots gives 50× margin under estimated 30-60s per batch. Single-batch failure recoverable via Retry button (Phase E). |
| Photo signed-URL approach abandoned for direct admin-client download | Server fetches via Supabase admin client to avoid double-egress + signed-URL TTL coordination. Spec §3.5 captures this. |
| Vercel Blob 24h cleanup cron not running | Cron registered alongside existing `cleanup-orphan-lots`. Manual smoke test in G3. |
| Browser collapses multiple anchor downloads | Sequential approach (wait for each to start before next) avoids browser anti-spam blocks. Each batch download triggers when its `/batch` POST resolves. |
| User closes tab mid-export | Each completed batch zip is already in Vercel Blob. User can re-trigger export, but won't resume — full restart. Document in user-facing copy. Acceptable given 5-15 min total time. |
| Re-export naming collisions | `addRandomSuffix: false` in Vercel Blob `put` overwrites prior export of the same job. User's local download folder gets browser auto-rename `(1)`. Document but don't gate. |
| Existing photos somehow non-JPEG (HEIC slipped through cataloging) | Storage bucket MIME-restricted at upload time + iPhone "Most Compatible" setting + cataloging UI. Unlikely. Server returns explicit `EXPORT_FAILED` per affected batch with lot numbers. |
| `start_bid` numeric serialization | Drizzle returns numeric as string by default; CSV formatter accepts string and `.toFixed(2)` handles both. Tested in A6. |
| Disabled customer's open jobs still appear in inventory filters | Intentional — disabled status is forward-looking (no new lots), not retroactive. Existing jobs/lots unaffected. Documented in spec §3.2. |
