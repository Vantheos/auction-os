# Phase 3 Implementation Plan — Mobile Cataloging + Photo Pipeline + Mobile Inventory

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended for token-budget reasons) or `superpowers:executing-plans`. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the warehouse-primary surfaces. Mobile cataloging (5 screens), photo capture pipeline (browser → Supabase Storage with IndexedDB queue), mobile inventory page (sticky search + filter sheet + full-screen modal), virtualized infinite scroll on inventory, login routing + role gating, cleanup-sweep cron.

**Architecture:** Native Vercel `(req, res)` handlers (Phase 1 pattern). Frontend continues React + Vite + React Router + TanStack Query + shadcn primitives + Mica Slate tokens. New routes are code-split. New deps: `idb-keyval` (IndexedDB wrapper, ~1 KB), `@tanstack/react-virtual` (~5 KB). All mutations through `asActor(userId, fn)`.

**Spec reference:** `docs/superpowers/specs/2026-05-01-phase-3-design.md` is authoritative.

**Branch:** `phase-3-mobile-cataloging` off `phase-2-lot-lifecycle` (a207122).

## Phase B — Backend endpoints

### B1. `api/lots/index.ts` — POST: add advisory lock + atomic first-photo creation
- [ ] Add zod field `firstPhoto: { displayOrder: z.literal(1) }` (optional) to `CreateSchema`
- [ ] In POST handler, wrap insert in `asActor(...)` block:
  ```ts
  await tx.execute(sql`SELECT pg_advisory_xact_lock(hashtext(${parsed.data.jobId}))`);
  const nextLotNumber = ...; // existing reservation
  const [lotRow] = await tx.insert(lot).values({...}).returning();
  let firstPhoto = null;
  if (parsed.data.firstPhoto) {
    const photoId = crypto.randomUUID();
    const [photoRow] = await tx.insert(lotPhoto).values({
      id: photoId, lotId: lotRow.id,
      storagePath: `lots/${lotRow.id}/${photoId}.jpg`,
      displayOrder: 1, status: 'pending', capturedBy: userId,
    }).returning();
    const { uploadUrl } = await signUploadUrl(photoRow.storagePath);
    firstPhoto = { ...photoRow, uploadUrl };
  }
  return { lot: lotRow, firstPhoto };
  ```
- [ ] Tests: concurrent POSTs with same `jobId` (race) — both succeed with sequential lot_numbers; the `LOT_NUMBER_CONFLICT` 409 path no longer fires under normal load (still defended)
- [ ] Tests: POST with `firstPhoto` returns lot + photo + uploadUrl atomically; without firstPhoto returns just lot

### B2. `api/lots/index.ts` — GET: add coverSignedUrl per row
- [ ] Modify the joined SELECT to also LEFT JOIN `lot_photo` where `display_order = 1` and pull `storage_path AS coverPath`
- [ ] After fetching rows, batch-sign all unique cover paths via `bulkSignReadUrls(paths, { width: 300, quality: 80 })`
- [ ] Attach `coverSignedUrl` to each lot in the response (or null if no cover)
- [ ] Update `LotDTO` in `shared/types.ts`

### B3. `api/lots/[id].ts` — DELETE: remove Storage objects
- [ ] Before DB delete, fetch all `lot_photo.storage_path` for the lot
- [ ] After successful DB delete (cascades photo rows), call `removeObjects(paths)`
- [ ] If Storage delete fails, log error but do NOT roll back the DB delete (the cleanup sweep would catch any orphans)
- [ ] Tests: delete a lot with N photos; verify both DB rows AND Storage objects removed

### B4. `api/lots/[id]/photos.ts` — POST: create subsequent photo
- [ ] Add POST handler (alongside existing GET)
- [ ] Body: `{ displayOrder: number }`
- [ ] Validate: lot exists, `displayOrder` is between current max+1 and 12
- [ ] In `asActor`: insert lot_photo with status='pending', generate signed upload URL
- [ ] Return `{ photoId, uploadUrl, storagePath, displayOrder, status }`
- [ ] Tests: insert valid photo; insert when count would exceed 12 → 422 `MAX_PHOTOS`

### B5. `api/lots/[id]/photos.ts` — GET: add signedUrl per row
- [ ] After fetching photo rows, bulk-sign their paths with `?width=1568&quality=80`
- [ ] Attach `signedUrl` to each photo in response

### B6. `api/lots/[id]/photos/[photoId].ts` — PATCH (status flip)
- [ ] Body: `{ status: 'uploaded' | 'failed' }`
- [ ] Validate: photo belongs to lot; status is a legal forward transition (`pending → uploaded` or `pending → failed`)
- [ ] Update via `asActor` (audit trail not needed for lot_photo per spec §4 but `asActor` keeps RLS consistent)
- [ ] Return updated row
- [ ] Tests: valid flips; reject `uploaded → pending`; reject mismatched lotId/photoId

### B7. `api/lots/[id]/photos/[photoId].ts` — DELETE
- [ ] Fetch the photo row (need its `storage_path`)
- [ ] Delete the DB row in `asActor`
- [ ] After commit, call `removeObjects([photo.storagePath])`
- [ ] If the deleted photo was cover (`display_order = 1`), promote next photo (if any) to cover by re-shuffling display_orders down by 1
- [ ] Tests: delete cover; verify next photo becomes cover; storage object removed

### B8. `api/lots/[id]/photos/order.ts` — PATCH (reorder)
- [ ] Body: `{ order: photoId[] }` — full ordered list of all photo ids for the lot
- [ ] Validate: array contains exactly the photos that belong to this lot (no missing, no extras)
- [ ] In `asActor` transaction: rewrite all `display_order` values in one statement (CASE WHEN id = ... THEN N ...)
- [ ] Tests: reorder N photos; mismatch returns 422

### B9. `api/cron/cleanup-orphan-lots.ts` — sweep handler
- [ ] `requireCronAuth(req)` first
- [ ] Query orphan lot ids:
  ```sql
  SELECT id FROM lot WHERE state IN ('assigned', 'unassigned')
    AND created_at < NOW() - INTERVAL '30 minutes'
    AND NOT EXISTS (SELECT 1 FROM lot_photo WHERE lot_id = lot.id);
  ```
- [ ] For each id: fetch any storage paths under `lots/{id}/` (typically none for true orphans), delete DB row (cascades), delete storage objects
- [ ] Wrap each lot's cleanup in a try/catch so one failure doesn't kill the batch
- [ ] Return `{ deleted: number, errors: number }`
- [ ] Register in `vercel.ts` crons array: `{ path: '/api/cron/cleanup-orphan-lots', schedule: '*/15 * * * *' }`
- [ ] Tests: seed orphans + valid lots; run sweep; verify only orphans deleted
